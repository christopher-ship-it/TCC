## 1. Background: why this is needed

TCC (Tecstellar Command Center) is the calling and customer-support tool used by the telecalling team. Agents call the app's customers to welcome new sign-ups, help people who got stuck, chase payments, answer support tickets and win back people who stopped using the app.

To do that, TCC needs to know about each customer: who they are, their phone number, when they signed up, how far they got, whether they are paying, whether they have a problem open, and when they last used the app.

Today that data lives only inside each app's own database, and the apps have **no way to share it** with another system. Customers have to be uploaded to TCC by hand from spreadsheets, which goes stale the same day.

The fix is for each app to expose a small, **read-only, key-protected HTTP API** that TCC calls on a schedule:

```
 ┌──────────────┐   HTTPS + API key    ┌─────────────────────────┐
 │     TCC      │ ───────────────────▶ │  Your app's backend     │
 │ (Tecstellar) │   GET  /customers    │  /api/tcc/v1/...        │
 │              │ ◀─────────────────── │  reads your own DB      │
 └──────────────┘   JSON customer list └─────────────────────────┘
```

- TCC **only reads**. It never creates, changes or deletes anything in your app.
- TCC asks every 5–15 minutes for "customers changed since my last check", and once a day for the full list (so anything missed heals itself).
- When a customer phones the call centre, TCC looks the number up to show the agent who is calling.

- List **every** HTTP endpoint the backend exposes today: method, path, what it returns, how it is protected.
- Is any endpoint already meant for **external** systems (other companies' servers), as opposed to the app's own screens?
- How are requests authenticated today? (User login tokens, Firebase ID tokens, session cookies, nothing?)

- Is there rate limiting, request logging, CORS configuration?

### 1.3 Where the customer data lives

For each field in **Section 4 (the customer record)**, find where the data is stored today: table/collection, column/field name, and type. Mark each one:

- ✅ **Exists** — stored and reliable.
- 🟡 **Derivable** — not stored directly, but can be computed (e.g. "open tickets" counted from a tickets table).
- ❌ **Missing** — the app does not record this at all.

Pay particular attention to:

- **Phone numbers:** what format are they stored in? (`+919876543210`, `9876543210`, `09876543210`, with spaces?) Are they unique per customer?

- **Soft deletes:** when a customer deletes their account, is the row removed or marked deleted?
- **Onboarding steps:** what are the steps a new user goes through, in order? Where is it recorded which step they reached?
- **Errors / drop-offs:** does the app record failed actions (payment failed, upload failed, KYC rejected, OTP not completed)?

### 1.4 Gaps and risks

- Which fields are ❌ missing, and what would it take to start recording them?
- Any data that **must not** leave the app (see Section 5)?
- Any performance concerns (e.g. no index on `updated_at` or `phone`, very large tables)?
- Anything in this guide that does not fit how the app works.

### 1.5 Proposed plan

A short list of the changes you intend to make in Phase 2, which files you will touch, and any database migration you will add.

## 3. Conventions used by every endpoint

| Topic | Rule |
|---|---|
| Base path | `/api/tcc/v1/` on your existing backend domain, e.g. `https://api.irondrobe.com/api/tcc/v1/` |
| Transport | HTTPS only. Reject or redirect plain HTTP. |
| Format | JSON, UTF-8. `Content-Type: application/json`. |
| Auth | Header `Authorization: Bearer <api key>` on every request. |
| Timestamps | ISO 8601 with time zone, UTC preferred: `2026-10-27T09:30:00Z`. Never "2 days ago" or local strings. |
| Phone numbers | E.164: `+919876543210`. If you store 10-digit Indian numbers, add `+91`. |
| Money | `{ "amount": 499.00, "currency": "INR" }`. Rupees, not paise. |
| Missing data | Use `null`. Do not omit the key, do not send `""` or `"N/A"`. |
| Field names | `snake_case`, exactly as written in this guide. |
| IDs | Your app's own stable customer ID, as a string. It must never change for the same customer. |
| CORS | Not needed — TCC calls from its server, not a browser. Do not enable CORS on these routes. |

### Errors

Every error uses the same shape and a correct HTTP status:

```json
{ "error": { "code": "invalid_api_key", "message": "API key is missing, wrong or revoked." } }
```

| Status | `code` | When |
|---|---|---|
| 400 | `bad_request` | Malformed parameter (bad date, limit out of range). |
| 401 | `invalid_api_key` | Key missing, wrong, or revoked. Same message for all three. |
| 403 | `forbidden` | Key valid but lacks the `tcc:read` scope. |
| 404 | `not_found` | Customer does not exist. |
| 429 | `rate_limited` | Too many requests. Include a `Retry-After` header (seconds). |
| 500 | `server_error` | Anything else. Never include stack traces or SQL in the message. |

### Field reference

**Required** fields must always be present and non-null. **Recommended** fields may be `null` if the app genuinely does not have the data — but each one missing makes the calling team less effective, so list them as gaps in the audit.

| Field | Need | Meaning |
|---|---|---|
| `id` | Required | Your stable customer ID. |
| `app` | Required | Fixed per app: `realbroks`, `irondrobe`, `influnet` or `vehigo`. |
| `name` | Required | Person's name as they entered it. |
| `phone` | Required | Main mobile number, E.164. TCC dials this number and uses it to match incoming calls. If a customer has no phone, leave them out of the API entirely. |
| `alt_phone` | Optional | Second number, E.164. |
| `email` | Optional | |
| `business_name` | Recommended | Shop / agency / brand name, if the app has one. |
| `customer_type` | Recommended | Who they are, in your app's own words (see **Appendix B** for the values TCC uses per app). Send your raw value; TCC maps it. |
| `city`, `state`, `pincode` | Recommended | Used to route the call to an agent who speaks the right language. Full state name, e.g. `Tamil Nadu`. No street address. |
| `preferred_language` | Recommended | App language the user chose, if any: `Tamil`, `Telugu`, `Kannada`, `Malayalam`, `Hindi`, `Bengali`, `English`. |
| `registered_at` | Required | When the account was created. |
| `last_active_at` | Recommended | Last time the user opened the app or did anything in it. Drives the "Inactive 30+ days" call list. |
| `app_version`, `platform` | Optional | `android`, `ios` or `web`. Helps support diagnose bugs. |
| `acquisition_source` | Optional | How they found the app (campaign, referral code, UTM source), if recorded. |
| `onboarding.stage` | Recommended | The furthest onboarding step reached, as a stable machine name (e.g. `registered`, `profile_completed`, `first_listing_created`). The full ordered list is returned by `/meta`. |
| `onboarding.completed` | Recommended | `true` once they have reached the point where the app is useful to them. |
| `onboarding.last_error` | Recommended | The most recent failed action that may have made them give up, or `null`. Drives the "Errors & drop-offs" call list. |
| `usage.primary_count`, `usage.secondary_count` | Recommended | The two numbers that best show whether the customer is getting value. They differ per app — see **Appendix B**. |
| `usage.last_action_at` | Optional | When they last did the primary action. |
| `plan` | Recommended | Current plan. Free users: `{ "name": "Free", "is_paid": false, … }` with other fields `null`. |
| `payment_due` | Recommended | Next or overdue payment, or `null`. `status` is `upcoming`, `overdue` or `expired`. `due_date` is a date (`YYYY-MM-DD`). Drives the "Payments & dues" call list. |
| `open_tickets` | Recommended | Support tickets / complaints that are not closed, newest first, **at most 5**. `[]` if none. Drives the "Tickets & flags" call list. If the app has no ticket system, send `[]` and note it in the audit. |
| `account_status` | Required | `active`, `blocked` or `deleted`. |
| `updated_at` | Required | When anything in this record last changed — see below. |
| `deleted_at` | Required | When the account was deleted, else `null`. |

### `updated_at` must be honest

TCC keeps itself in sync by asking "what changed since `updated_at` X?". So `updated_at` must move forward whenever **anything** in the record above changes — including things stored in other tables (a ticket is opened, a payment falls due, the user opens the app).

If those live in separate tables, compute it: `updated_at = max(customer.updated_at, latest ticket change, latest payment change, last_active_at)`. If that query is too slow, add a `tcc_updated_at` column and bump it from the places that write those tables. Explain which approach you chose in the handover note.

### How TCC uses these fields

So you know what matters most, here is how TCC builds each call list:

| TCC call list | Built from |
|---|---|
| New registrations | `registered_at` in the last few days and `onboarding.completed = false` |
| Tickets & flags | `open_tickets` not empty, especially `sla_breached = true` |
| Payments & dues | `payment_due` with status `upcoming` (soon) or `overdue` |
| Errors & drop-offs | `onboarding.last_error` set, or stuck at one `onboarding.stage` for days |
| Inactive 30+ days | `last_active_at` more than 30 days ago |
| Positive follow-up | Managed inside TCC; uses `usage` and `plan` to see progress |

## Phase 2 — Build the API

### 2a. API keys, stored in your database

Add a table (or Firestore collection) called `api_keys`:

| Column | Type | Notes |
|---|---|---|
| `id` | uuid / string | Primary key. |
| `name` | text | Who the key is for, e.g. `TCC production`. |
| `key_prefix` | text | First 12 characters of the key, shown in admin screens and logs so a key can be identified without revealing it. |
| `key_hash` | text | SHA-256 hash (hex) of the full key. **The full key is never stored.** |
| `scopes` | text[] / string list | For TCC: `["tcc:read"]`. |
| `created_at` | timestamp | |
| `last_used_at` | timestamp, nullable | Updated on use (at most once a minute is fine). |
| `revoked_at` | timestamp, nullable | Set to revoke. A revoked key stops working immediately. |

**Key format:** `<app>_live_` followed by at least 32 random bytes from a cryptographically secure generator, base62- or hex-encoded. Example shape: `irondrobe_live_4fQ9…` (do not use this example).

**Creating a key:** add a command-line script or an admin-only screen that generates a key, stores the hash, and **prints the full key once**. Example: `npm run tcc:create-key -- --name "TCC production"`. There must be no way to read a key back later — if it is lost, revoke it and make a new one.

**Revoking:** a matching `tcc:revoke-key --prefix irondrobe_live_4fQ9` command (or admin button). Allow two keys to be active at once so a key can be replaced without downtime.

**Checking a key on each request** (one middleware for all `/api/tcc/v1/` routes):

1. Read `Authorization: Bearer <key>`. Missing → 401.
2. Hash it with SHA-256, look up the row by `key_hash`, compare in constant time.
3. Not found or `revoked_at` set → 401 `invalid_api_key` (same message either way).
4. Scope `tcc:read` missing → 403.
5. Update `last_used_at`, then continue.

These routes must **not** accept normal user login tokens, and normal app routes must **not** accept these API keys.

**If the app has no backend of its own** (it talks straight to Firebase/Firestore or Supabase from the phone): build the API as a server-side function — Firebase Cloud Functions (HTTPS), Supabase Edge Functions, or a small separate service — using the admin/service-role SDK. Store `api_keys` as a collection that the mobile app's security rules **deny** all access to. Never put the service account or service-role key in the mobile app.

### 2b. Endpoints

#### `GET /api/tcc/v1/meta`

Tells TCC about the app, and doubles as a health check for the key.

```json
{
  "app": "irondrobe",
  "app_name": "IronDrobe",
  "api_version": "1.0",
  "server_time": "2026-10-27T09:30:00Z",
  "customer_types": ["Shop owner", "Individual"],
  "onboarding_stages": [
    { "stage": "registered",          "label": "Signed up" },
    { "stage": "profile_completed",   "label": "Filled shop details" },
    { "stage": "first_order_created", "label": "Created first order" },
    { "stage": "first_bill_printed",  "label": "Printed first bill" }
  ],
  "usage_labels": { "primary_count": "Orders", "secondary_count": "End customers" },
  "total_customers": 1342
}
```

`onboarding_stages` is in order, first to last.

#### `GET /api/tcc/v1/customers`

The list TCC syncs from. Query parameters:

| Parameter | Default | Meaning |
|---|---|---|
| `updated_since` | none | ISO timestamp. Only customers whose `updated_at` is **at or after** this. Omitted = everyone. |
| `include_deleted` | `false` | `true` also returns deleted/blocked customers, so TCC can hide them. TCC always sends `true` with `updated_since`. |
| `limit` | `200` | Page size, 1–500. |
| `cursor` | none | Opaque value from the previous page's `next_cursor`. |

Response:

```json
{
  "data": [ { …customer… }, { …customer… } ],
  "next_cursor": "eyJ1IjoiMjAyNi0xMC0yNVQxODo0MTowMFoiLCJpIjoidV84ZjJjOTEifQ",
  "has_more": true
}
```

**Paging rules** (get these right — wrong paging silently loses customers):

- Sort by `updated_at` ascending, then `id` ascending as a tie-breaker.
- Use **keyset (cursor) pagination**, not `OFFSET`: the cursor encodes the last row's `(updated_at, id)` and the next page starts strictly after it. Base64-encoded JSON is fine.
- When `has_more` is `false`, `next_cursor` is `null`.
- A customer updated while TCC is paging may appear again on a later page; that is fine (TCC de-duplicates by `id`). Missing a customer is not fine.

#### `GET /api/tcc/v1/customers/{id}`

One customer by your ID. 404 if not found. Deleted customers are returned with `account_status: "deleted"` (not 404), so TCC can show why they disappeared.

#### `POST /api/tcc/v1/customers/lookup`

Find a customer by phone number — used when a customer calls in. It is a `POST` with a JSON body so phone numbers do not end up in URLs and access logs.

Request:

```json
{ "phone": "+91 98765 43210" }
```

Response — always 200, with a list because one number can belong to more than one account:

```json
{ "data": [ { …customer… } ] }
```

Matching: strip everything except digits, then match on the **last 10 digits** against `phone` and `alt_phone`. So `+919876543210`, `09876543210`, `9876543210` and `+91 98765-43210` all find the same customer. Add an index (or a normalised column) so this is fast.

### 2c. Limits and logging

- **Rate limit** per key: 120 requests per minute is plenty. Above that → 429 with `Retry-After`.
- **Response time:** each page should return in under 2 seconds. Add indexes on `updated_at` and the normalised phone if they do not exist.
- **Logging:** log each request's time, key prefix, path, status and duration. **Never log the full key, the `Authorization` header, or request bodies** (they contain phone numbers).

## 5. Privacy and security — what must never be sent

The API shares personal data with Tecstellar's calling team for the purpose of supporting your customers. Send only the fields in Section 4. In particular, **never** include:

- Passwords, password hashes, OTPs, login/session/refresh tokens, push-notification tokens.
- Card numbers, bank account numbers, UPI IDs, or any payment-provider secret.
- Government ID numbers or documents (Aadhaar, PAN, driving licence, KYC images).
- Full street addresses, precise GPS location.
- Private messages or content customers wrote to each other.
- Internal admin notes not meant for support staff.

Build the response from an explicit list of allowed fields (a serializer / DTO / `select`). **Do not** return database rows or documents directly — new columns added later would leak automatically.

The app owner should make sure their privacy policy covers sharing customer contact details with their support and telecalling partner, as required under India's Digital Personal Data Protection Act, 2023.

## Phase 3 — Test it

Write automated tests in the project's existing test framework. At minimum:

**Auth**

- No `Authorization` header → 401.
- Wrong key → 401. Revoked key → 401. Same message for all three.
- A normal user login token → 401.
- Valid key → 200.

**Customers list**

- Returns the exact shape in Section 4; every required field present; no extra fields.
- None of the fields in Section 5 appear anywhere in the response (search the JSON for `password`, `token`, `otp`, `aadhaar`, `pan_number`, `upi`).
- Paging through everything with `limit=2` returns every customer exactly once (seed at least 5, some with the **same** `updated_at`).
- `updated_since` returns only customers changed at or after that time.
- Changing a related ticket or payment moves the customer's `updated_at` forward.
- Deleted customers appear only with `include_deleted=true`.

**Lookup**

- `+919876543210`, `9876543210`, `09876543210` and `+91 98765 43210` all find the same customer.
- Unknown number → `{ "data": [] }`.

**Manual check** against a running copy (replace the URL and key):

```bash
curl -s https://api.example.com/api/tcc/v1/meta -H "Authorization: Bearer $TCC_KEY"
```

```bash
curl -s "https://api.example.com/api/tcc/v1/customers?limit=2" -H "Authorization: Bearer $TCC_KEY"
```

```bash
curl -s -X POST https://api.example.com/api/tcc/v1/customers/lookup -H "Authorization: Bearer $TCC_KEY" -H "Content-Type: application/json" -d '{"phone":"9876543210"}'
```

## Phase 4 — Hand over to Tecstellar

When the API is deployed to production:

1. Create a production key named `TCC production` with the create-key command.
2. Send Tecstellar:
    - The base URL, e.g. `https://api.irondrobe.com/api/tcc/v1/`.
    - The `TCC_INTEGRATION_AUDIT.md` report, updated with what was built.
    - A short note: which fields are `null` or missing and why, how `updated_at` is computed, and the rate limit.
    - One sample response from `/meta` and one customer from `/customers` **with personal details replaced by fake values**.
3. Send the **API key separately** from everything else — by a password manager share or read out on a call. Never in the same email or chat message as the URL.

Tecstellar will connect TCC, run a full sync, and confirm the customer count matches `total_customers` from `/meta`.
